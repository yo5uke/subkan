# アーキテクチャ

SubKan は Kotlin + Jetpack Compose の単一 Gradle モジュール（`:app`）で構成された、完全オフラインの
Android アプリです。バックエンドはありません。

## 全体像

```
Compose UI  ──状態を受け取り、コールバックを返す──▶  ViewModel
                                                      │  StateFlow<UiState>
                                                      ▼
                                                  Repository ──▶ DAO ──▶ Room (SQLite)
                                                      │
                                                      └──▶ DataStore (設定)
```

データの流れは一方向です。DAO が返す Entity は Repository でドメイン型（`core/model`）に変換され、
ViewModel は `StateFlow<UiState>` を 1 本だけ公開します。Composable は状態を受け取ってコールバックを
返すだけで、Repository を注入することはありません。

## レイヤーごとの責務

| パッケージ | 責務 |
| --- | --- |
| `core/model` | ドメイン型と純粋なロジック（月額合計・並び替え・支払い日の判定）。Android 依存なし |
| `core/time` | `AppClock`。「今日」を差し替え可能にし、カウントダウン表示をテスト可能にする |
| `data/local` | Room の Entity・DAO・Database。カラム名（`snake_case`）は Entity が持つ |
| `data/repository` | Repository インターフェースと `Offline*` 実装。UI は DAO に触れない |
| `data/preferences` | DataStore による設定の永続化 |
| `data/icon` | サービス名 → ロゴ URL の解決。純粋関数 |
| `data/reminder` | AlarmManager による通知のスケジュールと、2 つの BroadcastReceiver |
| `data/di` | Hilt モジュール |
| `ui/` | Compose 画面・コンポーネント・テーマ |

`core/model` を Android 非依存に保つのは意図的な制約です。金額と日付という、このアプリで最も間違えたく
ないロジックが集まる場所であり、Robolectric なしの高速な JVM テストで守れるようにしています。

## ライブラリの選定理由

| ライブラリ | 用途 | 選んだ理由 |
| --- | --- | --- |
| **Jetpack Compose + Material 3** | UI 全体 | Material Design 3 を「テーマとして被せる」のではなく、コンポーネントとカラーロールのレベルで本格導入するため。ダイナミックカラーもここから来る |
| **Room** | サブスク・カードの永続化 | スキーマが JSON にエクスポートされ、マイグレーションを差分レビューできる。外部キー制約（`ON DELETE SET NULL`）を DB 層で表現できることが決め手 |
| **DataStore (Preferences)** | 設定 | テーマ・タブ位置・並び替えなど少数のスカラー値のみ。SharedPreferences と違い `Flow` で読めるので、テーマ変更が即座に画面へ伝わる |
| **Hilt** | DI | Repository と `AppClock` を差し替え可能にし、テストで偽時計を注入できるようにするため |
| **Coil 3** | サービスロゴの取得・キャッシュ | Compose ネイティブ。ディスクキャッシュを内蔵しており、Flutter 版の `cached_network_image` に相当する |
| **Navigation Compose** | 画面遷移 | 一覧 → 設定 → カード管理の 2 階層のみ。カードタブは遷移ではなくフィルタなので Pager で表現している |

## データモデル

### `payment_cards`

| カラム | 型 | 備考 |
| --- | --- | --- |
| `id` | TEXT (PK) | 初期カードは `c1`〜`c7`、以降は UUID |
| `name` | TEXT | 例: 楽天カード |
| `color_hex` | TEXT | `#` とアルファを含まない 6 桁（例: `BF0000`） |
| `sort_order` | INTEGER | タブの並び順。並び替え時に全件書き換え |
| `created_at` / `updated_at` | INTEGER | エポックミリ秒 |

初回起動時に 7 枚のカードを投入します（`seedDefaultsIfEmpty()`）。カードが 1 枚も無いとサブスクを
保存できないため、空の状態で「保存できないフォーム」を見せないための措置です。全件削除した場合に
復活はしません。

### `subscriptions`

| カラム | 型 | 備考 |
| --- | --- | --- |
| `id` | TEXT (PK) | UUID |
| `name` | TEXT | サービス名。ロゴ解決のキーも兼ねる |
| `price` | REAL **NULL可** | NULL は「金額未入力」。後述 |
| `is_estimated` | INTEGER | 1 なら概算。表示時に「約」を付ける |
| `currency` | TEXT | `JPY` / `USD` / `EUR` |
| `billing_cycle` | TEXT | `Monthly` / `Yearly` |
| `next_payment_epoch_day` | INTEGER | エポック日。**時刻ではない** |
| `card_id` | TEXT NULL | `payment_cards.id` への外部キー、`ON DELETE SET NULL` |
| `created_at` / `updated_at` | INTEGER | エポックミリ秒 |

### なぜ金額が `REAL` なのか

年額プランの月額換算は `price / 12` であり、本質的に割り切れません。整数の最小単位で持つと、
表示のたびに丸め位置を選ぶ必要が出てきます。SubKan は通貨をまたいだ加算を一切行わない
（通貨ごとに合計を並べる）ため、丸めは表示の 1 回だけに集約でき、`Double` で困りません。

### 金額が「未入力」「概算」「確定」の 3 状態を取る理由

光熱費のように毎月の金額が変わるものも登録できるようにするためです。想定する使い方は 2 通りで、
どちらを選ぶかはユーザーが登録時に決めます。

- **確定している金額だけを合計に出したい人** — 件名だけ登録し、金額は空のままにする
- **概算でも金額感を知りたい人** — 目安の金額を入れ、「概算」をオンにする

そのため `price` は NULL 可です。0 を「未入力」の代わりに使わない理由は、0 円のサブスク（無料期間中
など）と区別できなくなるうえ、どこか 1 箇所でも 0 として扱えば合計に紛れ込むからです。

| 状態 | `price` | `is_estimated` | 一覧での表示 | 月額合計への寄与 |
| --- | --- | --- | --- | --- |
| 未入力 | NULL | 0 | `—` | なし（0 円ではない） |
| 概算 | 値あり | 1 | `約¥4,000` | あり |
| 確定 | 値あり | 0 | `¥1,480` | あり |

「約」の表示は設定で消せます（既定は表示）。消しても保存されているデータは変わりません。

### 金額の表記（記号／日本語）

設定で 2 通りを切り替えられます。既定は記号です。

| 表記 | JPY | USD | 概算のとき |
| --- | --- | --- | --- |
| 記号（既定） | `¥1,480` | `$20` | `約 ¥4,000` |
| 日本語 | `1,480円` | `20ドル` | `約4,000円` |

記号のときだけ「約」との間に空白を入れています。記号も「約」も前置きの修飾子なので、詰めると
2 つの接頭辞が続いて読みにくくなるためです。日本語表記では単位が後ろに付くので、この問題は
起きません。

### 「約」を金額の文字列に連結しない理由

`"約" + "¥4,000"` のように 1 つの `Text` にまとめると、**その行だけ高さが変わります**。Latin
主体の文字列に CJK の「約」が混ざるとフォントフォールバックで和文フォントが選ばれ、その
ascent / descent が Latin より大きいため行ボックスが伸びるからです。結果として
`約 ¥10,000` と `$20` が同じリストの中で違う高さに見えます。

そのため `ui/components/AmountText` では「約」を**独立した `Text`** として並べ、数値側は Latin の
ままにしています。「約」は数値より小さいサイズなので、行の高さを決めるのは常に数値側です。

通知だけは連結しています。通知テキストにはレイアウトがなく、隣に高さを揃える相手もいないためです。
「約」の文字列リソースが 2 系統あるのはこのためです。

### 合計の「概算」表示

合計は「概算そのもの」ではなく「概算を含む」ものなので、金額の前には何も付けません。代わりに
ラベルの横に「概算含む」チップを出します。カード別タブのラベル（「〈カード名〉の月額」）は
カード名次第で長くなるため、ラベル本文を伸ばさないチップ形式にしています。

### なぜ支払日が「日付」なのか

ユーザーが選んだのはカレンダー上の日付です。インスタントとして保存すると、タイムゾーンが変わった
だけで「毎月5日」が 4 日になり得ます。エポック日で保存し、Material の日付ピッカーとの変換は
`ZoneOffset.UTC` を経由します（`ui/util/DateFormatting.kt`）。

## カード削除の 2 つの意味

このアプリで最も壊れやすい不変条件です。

| 起点 | 動作 | 実装 |
| --- | --- | --- |
| カードタブの長押し → 削除 | カードと**紐づくサブスクをすべて削除**。ダイアログで件数を提示 | `deleteWithSubscriptions()` がトランザクション内で明示的に削除 |
| 設定 → 支払いカードの管理 → 削除 | カードのみ削除。**サブスクは残り**「不明なカード」表示になる | 外部キーの `ON DELETE SET NULL` に任せる |

どちらも取り消し可能で、削除**前**に何を消すかを `DeletedCard` に記録します。行が消えた後では、
どのサブスクがそのカードを指していたかを DB に問い合わせる術がないためです。

外部キーを `CASCADE` に「整理」すると、後者が静かに破壊的な削除に変わります。

## 月額合計の算出

1. 表示中のタブでサブスクを絞り込む（タブ 0 =「すべて」）
2. 年額プランは `price / 12` に換算
3. **通貨ごとに**合計し、JPY を先頭・以降はアルファベット順に並べる
4. 表示時に一度だけ丸める

通貨をまたいだ換算・加算は行いません。為替レートを持たないアプリが「合計 ¥12,345」と表示するのは
嘘になるためです。複数通貨がある場合は `¥3,000 + $15` のように並記します。

## スワイプ中の合計表示

サマリーヘッダーは `pagerState.currentPage` ではなく
`currentPage + currentPageOffsetFraction` を丸めた値を見ています。前者だとページが確定するまで
合計が更新されず、スワイプ中に「すべて」の合計が残り続けます（v1.0.2 で修正した不具合）。

## テーマ

シード色 `#6750A4` は Material 3 のベースラインパレットと同一のシードです。そのため
`ui/theme/Color.kt` は 60 個の色を手書きせず、Compose の `lightColorScheme()` /
`darkColorScheme()` の既定値をそのまま使っています。ブランド色を変える場合は、この 1 行の
ファイルではなくトーナルパレットを組み直す作業になります。

ダイナミックカラー（Android 12 以降）は**既定でオフ**です。ランチャーアイコンが同じ紫であり、
壁紙由来の配色に置き換わるのはユーザーが選んだときだけにしたいためです。

例外的に配色ロールに従わない色が 2 つあります。どちらも `ui/theme/` 内に定義され、理由がコメント
されています。

- `cardColor()` — ユーザーがそのカードに選んだ色。テーマで変わってはいけない
- `serviceAccentColors()` — ロゴが無いサービスの代替タイル。ブランドロゴの代役なので、目立って
  安定していることが役割

## サービスロゴの取得

`ServiceIconUrl.forServiceName()` は、次のいずれかの場合にのみ URL を返します。

1. 既知サービスのキーワードに一致（公式ドメインを使用）
2. ユーザーがドメイン形式（`example.com`）で入力した

いずれにも当てはまらない場合は `null` を返し、呼び出し側が頭文字タイルを描きます。Google の
favicon サービスは未知のドメインに対して汎用の地球儀アイコンを返すため、「分からないなら URL を
返さない」ほうが、同じ地球儀が並ぶより見やすいという判断です。

URL は Google の favicon エンドポイントを画像プロキシ `wsrv.nl` 経由で取得します。リダイレクトを
追従し、サイズと形式を統一してくれるためです。

## 支払日の通知

前日の夜と当日の朝に、その日に引き落とされるサブスクをまとめて通知します。時刻と ON/OFF は
前日・当日それぞれ独立して設定できます（既定は前日 20:00・当日 8:00、どちらも ON）。

通知本文は件数で 3 段階に変えています。1 件なら金額、2〜6 件なら名前の一覧と合計、7 件以上は
合計だけです。件数はタイトルが伝えているので、それ以上並べても読みづらくなるだけだからです。

### アラームは「サブスクごと」ではなく「通知の種類ごと」に 1 本

登録数がいくつであっても、アラームは**常に 2 本**です。アラームは「前日通知か当日通知か」だけを
持ち、*何が対象か*は発火時にデータベースへ問い合わせます。

この設計から得られるもの:

- サブスクを追加・編集・削除してもアラームの再設定が一切不要
- 同じ日に 5 件の支払いがあっても通知は 1 通（「明日は 3 件の支払日です」）
- 登録数が増えてもアラーム数が増えない

### 繰り返しは「導出」であって、保存値は書き換えない

`next_payment_epoch_day` はアンカー（基準日）であり、支払日を過ぎてもアプリはこれを更新しません。
実際の次回請求日は `nextOccurrenceOnOrAfter()` が支払いサイクル分だけ進めて求めます。保存値のまま
使うと、**各サブスクにつき生涯 1 回しか通知されません**。

保存値を書き換えない理由は、月末の扱いにあります。アンカーが 31 日のとき、2 月は 28 日に丸めて
扱いますが、アンカー自体は 31 日のまま残ります。もし丸めた結果を書き戻すと、一度 2 月を通過した
だけでアンカーが恒久的に 28 日へずれてしまいます。

この導出は通知だけでなく、**一覧のカウントダウンバッジと「支払日順」の並びも**通ります
（`Subscription.nextChargeDate()`）。同じ関数を見ているので、通知と画面が違う日付を指すことは
ありません。

そのため「済」バッジはありません。次回請求日は常に今日以降になるため、到達しない状態です。
「済」はもともと日付が進まないことの副作用として見えていたもので、繰り越しを入れた時点で
意味を失いました。

### 正確なアラームは使わない

`setAndAllowWhileIdle()` を使い、`setExactAndAllowWhileIdle()` は使いません。後者は
`SCHEDULE_EXACT_ALARM` 権限が必要で、ユーザーへの権限ダイアログが 1 つ増えるうえ Play の
ポリシー上も制限があります。支払いのお知らせが 20:00 から数分ずれても実害はなく、
`setAndAllowWhileIdle()` は Doze 中でも発火します。

### 再スケジュールの契機

AlarmManager は再起動でアラームを失い、アプリ更新でも失います。時刻・タイムゾーンの変更では
失われませんが、「20:00」が指す瞬間が変わるため再計算が必要です。

| 契機 | 実装 |
| --- | --- |
| 通知が発火したとき | `ReminderReceiver` が最後に必ず再設定（`finally` 内） |
| 再起動・アプリ更新・時刻/タイムゾーン変更 | `ReminderBootReceiver` |
| 設定変更（ON/OFF・時刻） | `SettingsViewModel` が書き込み後に再設定 |
| アプリ起動時 | `SubKanApplication`（強制停止でアラームが消えた場合の保険） |
| 通知権限が付与されたとき | `MainViewModel.rescheduleReminders()` |

### 通知権限

`POST_NOTIFICATIONS`（Android 13 以降）は初回起動時に 1 度だけ要求します。「要求済みかどうか」は
設定に保存しています。システムのダイアログは 1 度しか出ないため、アプリからは「拒否された」と
「まだ聞いていない」が区別できないからです。

このフラグは既存インストールでは未設定なので、**通知機能を入れる前からアプリを使っている人も、
次に開いたときに権限を求められます**。

権限はアプリの外（端末の設定）でいつでも変更でき、変更を知らせてくれる仕組みもありません。そのため
`ON_RESUME` のたびに再確認し、許可されていればアラームを再設定します。ダイアログではなく設定画面から
許可した場合に通知が動き出すのは、この経路だけです。

許可されていない状態で通知が ON になっている場合は、設定画面に警告行を出して端末の設定へ誘導します。

## テスト

| 対象 | 場所 | 実行環境 |
| --- | --- | --- |
| 月額合計・並び替え・支払い日判定・アクセント色 | `app/src/test/java/com/subkan/core/model/` | 素の JVM |
| 繰り返しの導出・通知のスケジュール計算 | `core/model/PaymentReminderTest.kt` | 素の JVM |
| ロゴ URL の解決 | `app/src/test/java/com/subkan/data/icon/` | 素の JVM |
| 設定の既定値と永続化 | `data/preferences/SettingsRepositoryTest.kt` | 素の JVM（実 DataStore） |
| カード削除の 2 経路・取り消し・並び替え | `app/src/test/java/com/subkan/data/repository/` | Robolectric + インメモリ Room |

`SettingsRepositoryTest` は 1 テストにつき書き込み 1 回に抑えています。DataStore は `.tmp` を
リネームして書き込むため、Windows では連続した 2 回目のリネームが最初のハンドル解放前に走って
失敗するためです（Android 実機では起きない、JVM ホスト側の癖）。分単位への変換そのものは
`PaymentReminderTest` で直接検証しています。

カード削除だけが実際の SQLite を使うのは、それを成立させている `ON DELETE SET NULL` が Kotlin では
なくスキーマの性質だからです。DAO をモックすると、テストは通るのにアプリは壊れます。
